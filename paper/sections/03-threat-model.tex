\section{System and Threat Model}
\label{sec:threat}

\subsection{Self-Writing Agent Memory}

The system under study is an agent that stores memory records locally. Each record consists of
text, optional metadata, and an embedding vector produced by a public embedding model. Retrieval
returns the records whose embeddings are most similar to a query embedding. Four properties
distinguish this workload from the usual setting of searchable encryption, in which a user
outsources a document collection to a remote server.

Records are \emph{self-authored}, produced as a by-product of the agent's work and never reviewed,
and \emph{continuous}, written throughout the life of the store rather than in an initial bulk load.
They are \emph{inducible}: a party who can supply tasks to the agent, through a web page, a ticket
or an email, causes records to be written without any access to the store, and those records are
genuine agent output that content filtering cannot separate from organic ones. And the store is
\emph{local}, so the client/server distinction on which the security analysis of schemes such as
Sophos \cite{bost2016sophos} relies does not apply: both reside on the same disk.

With no remote server that must hold the index, the disk can be removed from the query path
altogether; \cref{sec:mnemos-m} takes that option.

\subsection{Partitioned Encrypted Vector Indexes}

An inverted-file (IVF) index divides the embedding space into $B$ partitions using a table of
centroids, called the \emph{partition table}. A record is assigned to the partition with the
nearest centroid. A search computes the $k_{\mathrm{probe}}$ partitions nearest to the query,
scores the records they contain, and returns the $\mathit{top\_k}$ best matches. Because
partitions are defined by embedding similarity, records on similar topics share partitions.

An encrypted variant seals each record, so that record contents require a key. Writes are
typically buffered and flushed in batches of $w$ records, called \emph{epochs}. The
analysis distinguishes two storage layouts. In an \emph{unpadded} layout, each partition occupies
a file region whose size is proportional to the number of records it holds. In a \emph{padded}
layout, each partition occupies exactly $C$ slots regardless of occupancy. A forward-private scheme
additionally maintains per-partition state such as update counters. Cohort H is the records
written before the compromise time $\tau$ and cohort P those written after; \advhist{} and
\advpost{} are topic-recovery advantage on each. The supplementary material tabulates the notation.

\subsection{The \texorpdfstring{$\tau$}{tau}-Arrival Adversary}
\label{sec:tau-adversary}

The adversary gains access to the stored state at an arbitrary time $\tau$ and retains it. Before
$\tau$ it observes nothing directly. At $\tau$ it obtains a copy of the on-disk state. After
$\tau$ it observes storage-level activity and may induce writes up to a budget $\beta$. It cannot
read the memory of the agent process while the store is unlocked and cannot extract keys from the
hardware key store.

What it observes after $\tau$ depends on how it obtained access, so the paper distinguishes two
classes.

\begin{itemize}
\item \textbf{W, the write observer.} A compromised synchronization or backup account, or repeated disk
imaging. It sees a sequence of file \emph{versions}, so it learns which byte ranges changed
between captures and when. It does not see reads at all: no search a local process performs
produces a new file version. This is the class the anchoring instantiations belong to.
\item \textbf{RW, the read-write observer.} A storage component with file-system visibility but no code
execution as the user, principally a network-share or remote-filesystem server that mediates the
store's reads and writes. It sees the same writes and additionally every read offset. Search-side
leakage matters only for this class. We deliberately do \emph{not} instantiate RW as a malicious
local storage driver: a kernel-mode driver can read the unlocked process's memory, which violates A3
and collapses the distinction the model is built on, so it is out of scope rather than a weaker RW.
\end{itemize}

\Cref{tab:tau} summarizes the two views; \cref{sec:eval} labels every result with its class. The
classes and the version-retention, OS-artifact and hibernation capabilities below are distinct
powers: a sync account retains versions but sees no reads, a network-share server sees reads but
retains no history, and an imaging adversary obtains artifacts but observes nothing live. A design
is credited with closing a channel only against the class that can observe it.

\paragraph{Why induction rather than exfiltration}
An adversary who can put content in front of the agent could instead try indirect prompt injection
\cite{greshake2023injection}. The two abilities come apart where this attack applies. A memory
pipeline such as mem0's extraction step has \emph{no tools and no egress}: it reads the document,
decides what to store, and writes, so injected instructions have nothing to act on. And injection
defenses --- egress gating, hardened summarizers, sandboxes that block tool use on untrusted content
\cite{debenedetti2025defeating} --- stop the agent from \emph{acting} on content, not from
\emph{remembering} it. Where injection is undefended it dominates; the storage channel is the
residual threat where it is defended.

Hardware key custody (\cref{sec:mnemos-keys}) protects a copy read offline; malware running as the
user can ask the key store to unwrap the master key, and is out of scope for every storage design.

\paragraph{Capture granularity}
\label{sec:granularity}
A synchronization client coalesces changes at an interval set by the client and network, not the
store, so the attacks are parameterized by the capture granularity $g$, the number of flushes between
versions the adversary obtains; coarser capture weakens every write-channel attack against W.

\subsection{Pre-\texorpdfstring{$\tau$}{tau} State a Real System Retains}
\label{sec:artifacts}

Ordinary artifacts record activity before $\tau$: the NTFS change journal records when the
store's files were written, and shadow copies, file-history snapshots and an SSD's flash
translation layer, which retains superseded pages \cite{wei2011reliably}, preserve earlier
contents (\cref{sec:eval-artifacts} audits them). The model therefore grants the adversary the
state at $\tau$ \emph{and} whatever earlier state these artifacts preserve. History independence in
the sense of Naor and Teague \cite{naor2001anti} is a single-snapshot notion and does not bound what
a \emph{sequence} of representations reveals; a synchronization account that retains versions
moves the effective compromise boundary back to the start of its retention window
(\cref{sec:attack-multisnapshot}, countermeasure in \cref{sec:mnemos-write}).

\paragraph{Hibernation}
A hibernation image captures a locked arena and the unwrapped master key, since locking pages
prevents paging but not hibernation. Locking the store and zeroizing its arena on suspend and
hibernate notifications is therefore a deployment requirement, and the guarantee is conditional on
the operating system delivering that notification.

\subsection{Assets, Goals, and Assumptions}

The assets, in decreasing order of sensitivity, are the content of stored records, their topics, the
temporal pattern of the agent's activity, and the existence of specific records; a record's topic,
meaning the subject matter the agent worked on, is often as sensitive as its text and is easier to
recover. The security goals are content confidentiality, topic confidentiality for cohort P, query
privacy under observation of storage access, resistance to correlation of induced writes, and topic
and membership confidentiality for cohort H, which is the focus of this paper.

The analysis assumes secure cryptographic primitives (A1); a host uncompromised before $\tau$ (A2),
without which cohort H does not exist and the problem reduces to that of a fully observed store;
that the adversary neither defeats hardware key custody nor reads the memory of the unlocked agent
process (A3), which is what makes a memory-resident design possible at all and which
\cref{sec:mnemos-m} takes at face value rather than paying for on-disk search the threat model does
not require; a public embedding model, with no security derived from its secrecy (A4); and a finite
injection budget (A5), as a function of which results are reported. Availability, the integrity of
agent behavior, microarchitectural side channels, and deployments spanning multiple hosts are out of
scope.

\paragraph{Passive versus active storage}
The adversary of this paper is passive at the storage layer: it reads versions and induces writes
through the agent, but does not itself modify, roll back, or fork the stored files. A compromised
synchronization account could do all three, and tampering is a membership channel in its own right
--- corrupt the region an earlier record would occupy and watch whether the agent later errs on that
topic. We scope tampering out of the confidentiality analysis for a stated reason: every slot is an
authenticated ciphertext (S2), so a tamper surfaces as an authentication failure. Mnemos-M reads the
whole store at unlock and fails closed, independently of content; Mnemos-P fails when a search probes
the region, which the RW class observes. Authentication does not detect rollback to an authentic
earlier version; a hardware monotonic counter bound into the manifest's associated data is the
standard defense, and we leave it to future work.
