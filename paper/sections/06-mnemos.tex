\section{A Design Space}
\label{sec:mnemos}

\Cref{thm:main} gives conditions a layout can satisfy, \cref{prop:capacity,prop:derived} give two a
content-placed layout cannot, and \cref{thm:reactive} gives the conditions that survive a reactive
agent. The design principle that follows is that \emph{semantic indexing need not imply semantic
physical placement}. The designs below sit at different points of that space; all are implemented in
Rust, with a Python binding used only by the evaluation harness and the embedding model.

\begin{itemize}
\item \textbf{Mnemos-RS:} a record store plus a separate index, the natural padded design.
\item \textbf{Mnemos-P:} one sealed file of $B$ equal regions, placed by content, searched on disk.
The construction \cref{thm:main} is proved for.
\item \textbf{Mnemos-M:} the same sealed file, placed independently of content, searched in memory,
and written by a clocked sweep. \textbf{Mnemos-M/disk} keeps headers and payloads on disk for stores
larger than memory.
\end{itemize}

\subsection{The Shared Layout}
\label{sec:mnemos-layout}

Mnemos-P and Mnemos-M share a file of $B$ equal regions of $C$ slots. A slot holds two
authenticated ciphertexts, a fixed-size header carrying the record identifier and its quantized
embedding and a fixed-size payload carrying the text and metadata. Every ciphertext uses
XChaCha20-Poly1305 under a fresh 192-bit random nonce; a header's associated data binds it to its
slot and format version, a payload's to its record. A free slot is uniformly random bytes. The file lengths are
functions of $B$, $C$, the embedding dimension and the block size, so S1 and S2 hold. The manifest,
which holds tombstones and the cursor, is itself one fixed-size authenticated ciphertext.

\subsection{Mnemos-P: Placement by Content}
\label{sec:mnemos-p}
\label{sec:mnemos-write}

A record's region is the keyed permutation of its nearest centroid's partition, so that an adversary
holding a public partition table cannot map a topic to a region directly; a secret rotation of the
centroids would not do this, since it preserves the nearest-centroid assignment. Against the RW
class the permutation is weaker than it appears, because regions read together are geometric
neighbours and the co-occurrence graph of reads can be matched to the public table
(\cref{sec:eval-permutation}); against W, which sees no reads, it holds.

A flush rewrites $w+1$ whole regions (S3), so a write reveals which region changed and never which
slot. A record whose partition is full is refused rather than spilled, and the refused write
performs the same region rewrite an accepted one would have (\cref{prop:capacity}). The whole file is
re-encrypted at lock, so a version diff spanning a session covers every region, and the maintenance
cursor restarts at a random position at each unlock, so its resting position does not count the
flushes before $\tau$.

\paragraph{Search} A search reads the regions of its probe set, ranks the decrypted headers in memory,
and decrypts the $\mathit{top\_k}$ payloads from the regions already read, so no result-dependent
access reaches the disk (\cref{sec:eval-search}). Every query reads the same number of regions: by
default its $k_{\mathrm{probe}}$ nearest partitions plus $(s-1)k_{\mathrm{probe}}$ fresh random
ones, or alternatively one of a fixed set of disjoint groups. Neither hides query equality
(\cref{sec:eval-query}); only grouping resists permutation recovery.
\label{sec:mnemos-read}

\subsection{Mnemos-M: Placement Without Content, Search in Memory}
\label{sec:mnemos-m}

Assumption A3 grants that the adversary cannot read the unlocked process's memory, and in the local
setting no server must hold the index. Mnemos-M takes both at face value.

\paragraph{Search} At unlock the store is read once, sequentially, and every header and payload is
decrypted into the locked arena. A search ranks the resident headers and returns resident payloads,
so it performs \emph{no disk access}: the search, result and query-equality channels are absent
rather than mitigated. Exhaustive ranking is linear in $n$, so Mnemos-M also keeps each record's
nearest-centroid partition in the arena and, when configured to, ranks only the query's $k$ nearest
partitions. The partitions are \emph{logical}: the disk layout does not change, and neither adversary
class observes the index. It costs recall (\cref{sec:eval-recall}) and unlock time
(\cref{sec:eval-perf}).

\paragraph{The sweep flush} Writes follow a deterministic write-only ORAM
\cite{roche2017detwooram}. Every $\Delta$ while the store is unlocked, whether or not anything was
written, the flush rewrites the next $k$ slots after a cursor, each as a fresh sealing: a live slot
is re-encrypted, a free slot either receives a staged record or is refreshed with random bytes. A
staged record waits in a fixed-size sealed journal, rewritten every flush, until the cursor reaches a
free slot. The cursor starts at a random position at each unlock and advances by $k$ per flush, so
the set of slots a flush writes is a function of the flush index alone (C1); every written unit is a
fresh fixed-length ciphertext (C2); and searches touch no disk (C3). \Cref{thm:reactive} therefore
applies. A record's position depends on the cursor and on which slots are free, never on its content,
and the occurrence of a flush no longer implies that the agent wrote, which closes the derived-write
channel. A staged record reaches its slot within one pass of the cursor; until then it is durable
in the journal, and a lock flushes until at most the journal's capacity remains staged.

\paragraph{Capacity} There is no per-partition capacity, so \cref{prop:capacity} does not apply; the
global bound is a function of the record count, which the game equalizes.

\paragraph{Mnemos-M/disk} For stores larger than memory, headers and payloads stay on disk and the
arena holds only the position map and each slot's logical partition, a few bytes per record. Writes are the sweep's, unchanged, so against W every write-side channel
remains closed at any size. A search reads the headers of its probed logical partitions, so RW sees
which slots were read: the read channel of any on-disk index, which only oblivious search closes.

\subsection{Deletion, Key Custody, and Instrumentation}
\label{sec:mnemos-delete}
\label{sec:mnemos-keys}
\label{sec:mnemos-events}

A deletion records a tombstone in the sealed manifest and writes nothing else at the call, so it
does not name the record's region; an update is a deletion plus a fresh write. Mnemos-P frees
tombstoned slots when its maintenance cursor rewrites their region, within $B$ flushes; Mnemos-M
frees them when the sweep reaches them, within one pass of the cursor in wall-clock time. Neither
reaches copies a synchronization provider already retains.

The master key is wrapped by a hardware key store, the Windows TPM through the CNG Platform Crypto
Provider, and unwrapped into a locked, promptly zeroized region only while the store is unlocked;
working keys are derived from it by HKDF. Custody is paired with a guard that locks every store on
the operating system's suspend notification (\cref{sec:artifacts}), tested with the broadcast
Windows sends before sleep.

Every disk-visible operation emits one typed event naming the file ranges it touched. That stream is
the transcript the attack harness consumes, so an attack cannot observe more than the storage
adversary does, and the byte-level auditor (\cref{sec:eval-audit}) checks the stream against the disk.
