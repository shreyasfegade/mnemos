# Mnemos synthetic data

Synthetic data for the Mnemos evaluation pipeline. Generated by `data/generate_data.py`,
**stdlib-only** (no numpy, no torch, no sentence-transformers) and **deterministic**:

```sh
python data/generate_data.py
```

A single seed (`20260812`, recorded in `manifest.json`) plus a per-file derived sub-seed
drives every random choice, so the files are byte-for-byte reproducible on any machine.
`manifest.json` records the generator version, the seed, and the SHA-256 of the `params.toml`
that was current when the data was produced, so any result derived from these files can be
traced back to the exact configuration that produced it.

---

## Files

| Path | Count | Role |
|---|---|---|
| `d3-swebench/notes.jsonl` | 5,000 | **D3 procedural-memory corpus** (`params.toml [datasets] d3_procedural`) |
| `d3-swebench/tasks.jsonl` | 1,200 | Induced-write / injection task stream (A4, E5, E6) |
| `retrieval-clusters.jsonl` | 1,500 | Semantically clustered retrieval fixtures |
| `manifest.json` | — | Machine-readable provenance (version, seed, params hash, schemas) |
| `generate_data.py` | — | The generator |
| `assemble.py` | — | (legacy, superseded) |

`D1` (Hermes self-authored memory) and `D2` (MS MARCO / NQ) are **not** generated here:
D1 is real agent output harvested by E7 (the specification T2), and D2 is a public corpus pulled by
its own script. This directory covers **D3 only**, plus the two supporting fixtures the
pipeline needs to exercise D3.

## 1. `d3-swebench/notes.jsonl` — the D3 procedural corpus (5,000)

Schema (one JSON object per line):

| Field | Type | Meaning |
|---|---|---|
| `note_id` | str | `d3-<topic>-<seq:05d>` |
| `topic` | str | One of the 10 clusters: `sql, networking, filesystem, concurrency, crypto, containers, web, debugging, algorithms, cloud` |
| `category` | str | `bugfix` \| `feature` \| `refactor` \| `performance` \| `hardening` |
| `difficulty` | str | `easy` \| `medium` \| `hard` |
| `language` | str | One of 12 languages, topic-weighted |
| `component` | str | Code-area noun (`parser`, `pipeline`, `worker`, …) |
| `source_task` | str | The task id this note is a distillation of |
| `tags` | list[str] | Topic + derived term tags |
| `written_at_ms` | int | Monotonic, strictly increasing across the file (epoch-flush realism) |
| `seq` | int | Global 0-based sequence number |
| `text` | str | The note itself — see below |
| `meta` | str | JSON-encoded `{category, difficulty, language, component, tags}` — matches the Rust `Memory.meta` shape (`mnemos-core::types::Memory`), which is JSON-encoded and encrypted alongside the text |

**Content.** Each note is a first-person "agent solved a coding task and wrote itself a
procedural note about it" entry, in the spirit of SWE-bench-style task logs distilled into
skill notes. Every note names concrete machinery (real flags, functions, error classes, and
configuration knobs per topic — `CREATE INDEX CONCURRENTLY`, `TCP_NODELAY`, `fsync` on the
directory, `Argon2id`, `RUN --mount=type=cache`, `SameSite=Strict`, `git bisect`, `union-find`
path compression, `DLQ` visibility timeouts) rather than generic advice, and ends with a
distilled reusable lesson plus a tag line pointing at the specific handling code. The verb
clause after the category action ("I fixed it by …") is drawn from a pool of seven varied
phrasings, so no single template sentence dominates the corpus, and the category verbs
themselves are audited to compose grammatically with the pronoun scaffold (no "cleaned up
it"-style artifacts).

**Distribution.** Exactly 500 notes per topic (10 × 500). Categories and difficulties are
weighted (bugfix-heavy, medium-heavy), and languages are topic-weighted — so a `sql` topic
skews toward Python/SQL and a `containers` topic toward Bash/Go, the way a real agent's corpus
would. `meta` is kept consistent with the top-level fields so downstream code can trust either
view.

**Why these shapes.** `params.toml` declares `d3_procedural = "data/d3-swebench"` and
the evaluation plan §5 calls for "SWE-bench-style task logs → procedural skill notes ~5k", so 5,000
is the agreed volume. The `text`/`meta` split mirrors `Memory { text, meta }`, and the
monotonic `written_at_ms` exists so the corpus can be written into a store in arrival order —
which is what the epoch-flush machinery (`params.toml [epoch]`) and the E5/E6 injection
experiments need.

## 2. `d3-swebench/tasks.jsonl` — induced-write task stream (1,200)

Schema:

| Field | Type | Meaning |
|---|---|---|
| `task_id` | str | `task-<topic>-<seq:03d>` |
| `topic` | str | Semantic topic of the task |
| `difficulty` | str | `easy` \| `medium` \| `hard` |
| `attack` | bool | **`true` for the injection segment** (last 20 of each topic's 120) |
| `trigger` | str | The verb+artifact stem an injected task must produce a predictable memory from |
| `tags` | list[str] | Topic + one domain term |
| `task` | str | The one-line directive, e.g. `"Query the audit_log in under 100 ms"` |

**Why a stream, and why tagged.** A4's adversary supplies a **task** to the agent and the agent
authors the memory (the adversary controls the stimulus, not the content). E5/E6 need to (a)
inject `m ∈ {1, 10, 100}` known tasks, (b) locate the resulting entries, and (c) check whether
they landed where expected. `topic` gives the analysis a ground-truth "where it should have
landed" label, and the final 20 tasks per topic form a **clearly-delimited injection tail**:
short directives that name a concrete artifact (`users_table`, `lambda_fn`, `job_queue`) so the
induced memories are semantically predictable while remaining realistic.

**Background vs. injection grammar is deliberately different.** The first 100 per topic read
like ordinary environment directives (`"Join the payments in under 100 ms"`); the attack tail
drops the article and names the artifact directly (`"Backfill across the events_table"`). The
attack harness can use either the `attack` flag *or* the text shape to select its injection
set, and the textual difference is itself the thing the leak analysis cares about.

## 3. `retrieval-clusters.jsonl` — clustered retrieval fixtures (1,500)

Schema:

| Field | Type | Meaning |
|---|---|---|
| `doc_id` | str | `clu-<cluster>-<seq:03d>` |
| `cluster` | str | Ground-truth topic label |
| `title` | str | A title from the cluster's pool |
| `text` | str | 3–6 sentences, **all drawn from the same cluster** |
| `words` | int | `len(text.split())` |

**Why.** Embedding/retrieval benchmarks are only meaningful against real semantic structure.
Each document's sentences are drawn from a single cluster's pool (no cross-cluster mixing), so
the 10 clusters are genuinely distinct and non-overlapping by construction. Retrieval
experiments can then measure Recall@10 and nDCG against a known ground truth: a query drawn
from cluster `X` should retrieve documents from cluster `X`, and cross-cluster hits are
measurable noise. Exactly 150 documents per cluster (10 × 150), each ≥ 30 words.

## 4. Judgment calls

- **5000 / 1200 / 1500** match the evaluation plan §5's "~5k" D3 target and the pre-existing
  `data/` scaffold (5k notes / 1.2k tasks / 1.5k clusters), so nothing downstream needs to
  change.
- **`attack` + `trigger` fields are additive.** The old scaffold had only `task`/`topic`.
  Adding these two fields is what makes the induced-write harness (A4/E5/E6) able to select
  semantically predictable injection tasks; both are populated for every task so a consumer
  that ignores them is unaffected.
- **10 topics, all technical, non-overlapping** (sql, networking, filesystem, concurrency,
  crypto, containers, web, debugging, algorithms, cloud). These are the same 10 the scaffold
  used, kept for continuity.
- **`meta` stays a JSON string**, not a nested dict, because `mnemos-core::types::Memory`
  stores metadata as an encrypted JSON-encoded string.
- **Monotonic `written_at_ms`** across the whole notes file (not just per topic), so the
  corpus can be replayed in arrival order for epoch-flush and injection experiments.
- **No external dependencies.** The generator is stdlib-only so `python data/generate_data.py`
  runs anywhere, including in CI, without a GPU or a model download.

## 5. Reproducing

```sh
python data/generate_data.py   # rewrites all four files under data/, then self-verifies
```

The script re-parses everything it writes and asserts counts, per-topic balance, field
presence, enum validity, `meta`↔top-level consistency, strict timestamp monotonicity, text
uniqueness (no duplicate notes/tasks/docs), and the attack-tail shape (exactly 20 of each
topic's 120 tasks flagged `attack`). A failed assertion means the output is wrong and nothing
is left half-written silently.
